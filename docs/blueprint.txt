Technical Research & Engineering Blueprint · Version 1.0 · November 2026

Project objective: Train two cooperating, specialized small language models that transform natural-language requirements into production-quality web interfaces, evaluate the rendered results, identify design and usability defects, and iteratively improve the generated code.

The ambition is to build something that can eventually compete with significantly larger UI-generation systems on design quality, while remaining relatively inexpensive to run and fully under our control.

I would treat this as both a serious machine learning research project and the foundation of a deployable software product.

There are only two trainable models in this architecture. The requirements compiler, browser renderer, test runner, and revision controller are deterministic software components, not third-party foundation models.

That is important: the system should not secretly depend on a much larger proprietary model during production.

It owns the source code. The Critic never writes directly to the project files.
The Critic must learn to assess interfaces, not merely recognize whether a screenshot looks attractive.

It receives the original user requirements, screenshots, interaction observations, and measured test results.

It outputs a structured, prioritized critique.

Its responsibilities are:
1. Detect visual and structural weaknesses.
2. Detect usability problems supported by observations.
3. Evaluate design consistency and prompt adherence.
4. Identify probable causes of defects.
5. Propose precise, actionable changes.
6. Recognize uncertainty and abstain where evidence is insufficient.
For example, it may say:
The primary call-to-action is visually subordinate to the secondary button. Increase its contrast and prominence without changing the information hierarchy.
But it should not claim a form is nonfunctional based solely on a screenshot. That requires interaction-test evidence.

The Critic should be trained to distinguish what it sees, what the tools measured, and what it merely suspects.

This is one of the project's most important scientific safeguards.

A candidate should be rejected or quarantined when:
- It does not compile or render.
- Its source cannot be used under the dataset's license.
- Its purported functional behaviors are untested.
- The screenshot does not match its source implementation.
- Its required assets are missing or inaccessible.
- It duplicates an evaluation example or substantially duplicates an existing training example.
- Its generated description misrepresents visible behavior.
We should also preserve some intentionally broken examples for Critic training, with explicitly labeled failure conditions.

Let the user specification be \(x\), and the target structured design and code response be \(y\).

We initially minimize token-level negative log-likelihood:
\[ \mathcal{L}_{A,\mathrm{SFT}} = -\frac{1}{\sum_t m_t} \sum_{t=1}^{T} m_t \log P_{\theta_A}(y_t\mid x,y_{<t}) \]
Here \(m_t\) masks everything except the assistant tokens we want to train on.

We should train on three task types, with explicit task identifiers:
- GENERATE: specification → complete implementation.
- PLAN: specification → typed design plan.
- REVISE: implementation + critique → corrected patch.
For the first experiment, use the same shared model weights for all three tasks rather than building three separate adapters. We can test separate adapters later if one task hurts another.

Why only 4,096 tokens initially?

Because we need to verify whether a small model can learn the design task at all before training on large multi-file applications. Many component-level examples fit within a manageable sequence length. Complete applications will require longer contexts or file-by-file generation.

Once the smaller experiments work, extend to 8,192–16,384 token contexts using length bucketing, memory profiling, and gradient accumulation.

We can implement this with Hugging Face Transformers, PEFT, TRL, and BitsAndBytes, validating against the installed library versions. The TRL documentation supports parameter-efficient SFT and preference training. 
Hugging Face

After SFT, generate multiple candidate designs for each held-out training prompt.

Humans compare implementations based on the same brief, rendered at the same dimensions.

For each pair, we obtain:
\[ (x,y^+,y^-) \]
where \(y^+\) is the preferred output and \(y^-\) is the rejected output.

We can train with DPO:
\[ \mathcal L_{\mathrm{DPO}} = -\mathbb E\left[ \log \sigma\left( \beta \left[ \log\frac{\pi_\theta(y^+\mid x)}{\pi_{\mathrm{ref}}(y^+\mid x)} - \log\frac{\pi_\theta(y^-\mid x)}{\pi_{\mathrm{ref}}(y^-\mid x)} \right] \right) \right] \]
Initial \(\beta=0.1\), with a validation sweep over 0.05, 0.1, and 0.2.

A major caveat: preference comparisons between enormous, independently generated codebases can have noisy credit assignment.

Therefore I would initially optimize short, scoped changes and design-plan selections, rather than assuming that DPO over entire multi-file projects will work well.

We will retain the SFT-only checkpoint and compare it directly against the DPO checkpoint.

A good Critic must not merely detect defects. It must rank their importance correctly.

Consider three issues:
- A 2-pixel icon misalignment.
- A mobile navigation menu that cannot open.
- A low-contrast primary button.
The first is cosmetic. The second blocks functionality. The third may affect both usability and accessibility.

The Critic should generally prioritize the blocking issue.

This is where the two models become a coherent system.
The loop should be strictly controlled.
```

def build_ui(spec, architect, critic, tools, max_revisions=3):
    project = architect.generate(spec)
    best = None

    for iteration in range(max_revisions + 1):
        evidence = tools.build_render_and_test(project)

        critique = critic.evaluate(
            specification=spec,
            screenshots=evidence.screenshots,
            test_results=evidence.tests,
            structure=evidence.structure,
        )

        issues = validate_critique(critique, evidence)
        candidate = evaluate_candidate(project, evidence, issues)

        if best is None or is_preferred(candidate, best):
            best = candidate

        if candidate.passes_release_gates:
            if not has_actionable_major_issues(issues):
                break

        if iteration == max_revisions:
            break

        patch = architect.revise(
            specification=spec,
            project=project,
            verified_issues=issues,
        )

        project = apply_in_sandbox(project, patch)

    return best

```
The above is algorithmic pseudocode. Its types, stopping rules, and preference comparisons must be implemented concretely.
Suppose the Critic suggests a larger heading and the Architect implements it.

The system must compare before-and-after outputs and verify that:
- The intended change occurred.
- The page still compiles.
- Existing interactions still function.
- No new overflow or accessibility failures occurred.
- Human or validated model judgments indicate actual visual improvement.
Otherwise the system could enter a cycle where each model agrees with the other's decisions, regardless of whether the interface improves.
Use two distinct revision modes.

Local revision: Change only an identified component or token when the problem is localized.

Structural revision: Permit changes across multiple components when the problem concerns navigation, information architecture, or overall layout.

Initially, the revision controller should default to local changes.

For example, if a card has inconsistent padding, the model should not rewrite the entire application.

The revision instruction should include an affected-file allowlist and a non-regression checklist.
Never allow unbounded self-refinement.

Once the isolated models work, we collect actual trajectories:
\[ x \rightarrow A_0 \rightarrow C_0 \rightarrow A_1 \rightarrow C_1 \rightarrow A_2 \]
Where:
- \(A_i\): Architect-generated artifact.
- \(C_i\): Critic feedback on that artifact.
We record the code changes, screenshots, test outcomes, and human preference results at each iteration.

Then we build two new training tasks.

Architect revision training: Given an earlier implementation and verified critique, predict an effective patch.

Critic revision-effect training: Given the original and revised implementation, predict what improved, what regressed, and what remains unresolved.

This is different from training the models merely to imitate their own outputs.

Only validated improvement trajectories should be promoted into the primary training dataset. Failed trajectories are useful as negative or diagnostic examples.

One important detail: when the Critic participates in selecting training examples, it must not also serve as the sole judge of subsequent performance. Independent human evaluation is essential to prevent circular self-reward.

Human judgments are the most important test of our central claim: that we generate great UI.

Use blind pairwise comparisons.

Each reviewer receives the same original brief and two rendered, functional interfaces, without knowing which system generated them.

They answer:
- Which interface looks better?
- Which better satisfies the brief?
- Which is easier to understand?
- Which would you prefer to use?
- What is the most important difference?

For the Critic, image processing and variable screenshot resolution may create substantially higher memory consumption than text-only training.

I would benchmark memory usage before selecting its final batch size and context length.
Instead of assuming training will require a fixed number of GPU hours, we should calculate the required steps from the actual data.

For example, if an accepted dataset contains 12,000 samples, the effective batch size is 32, and we train for two epochs:
\[ \text{Optimizer steps} = \left\lceil\frac{12{,}000}{32}\right\rceil \times 2 = 750 \]
But this tells us little about runtime without accounting for input/output token lengths, visual tokens, packing efficiency, and hardware throughput.

I would create a benchmark script that measures actual tokens per second, peak GPU memory, and wall-clock time for 25–50 representative optimizer steps.

Then the project can produce credible training-cost forecasts based on measured throughput.

Notice that we do not fine-tune either model in Sprint 1. That's intentional.

First, we need to understand the base models' capabilities and establish a scientifically defensible measurement system.

Training without that foundation would make improvements difficult to attribute or reproduce.
I see four potential research contributions.

1. Small-model design specialization. Demonstrate how specialized data changes the UI-generation quality of a 4B language model, including what capabilities improve and what capabilities remain weak.

2. Grounded multimodal design criticism. Train a compact VLM to identify interface problems and propose useful corrections using screenshots and verifiable behavioral observations.

3. Iterative two-SLM collaboration. Study whether a specialized generator and critic can jointly produce higher-quality interfaces than either model alone, controlling for inference compute and revision count.

4. A reproducible UI quality benchmark. Develop a benchmark spanning aesthetics, functionality, responsiveness, usability, and critique quality, including human judgments and regression measurements.

The benchmark and grounded critique dataset could themselves become valuable open research resources, subject to licensing and annotation-quality constraints.
To keep the first system scientifically tractable, I would exclude native mobile apps, full backend generation, real payment integrations, complex authentication flows, arbitrary npm dependencies, Figma round-tripping, and general-purpose computer-use agents.

We can support believable simulated data and local frontend state, but must clearly distinguish demonstrations from real external integrations.

I also would not train a third hidden judge model. The central research constraint is two specialized trainable models, with deterministic tests and independent human reviewers serving as external validation.
I would formalize the project around this hypothesis:
A 4B language model specialized in UI generation, paired with an independently fine-tuned 4B multimodal design critic and a bounded render–critique–revision loop, can produce measurably more usable, aesthetically preferred, and functionally correct web interfaces than the same generator without specialized critique.
We should test this claim without assuming that it is true.

The result could be a strong dual-SLM system, or it could reveal that model quality, data diversity, or visual preference learning is the real bottleneck. Both outcomes would be useful research findings.
I would prioritize the following three things above everything else:

First, build the deterministic rendering and testing infrastructure. It supplies trustworthy observations to the Critic and makes the whole system measurable.

Second, invest heavily in the Critic's dataset. Teaching a model to identify genuine flaws, ground its findings, and know when to abstain is likely to be harder than training the Architect to write frontend code.

Third, benchmark every stage independently. We want to know precisely whether better training data, preference optimization, multimodal criticism, or repeated revisions produce the improvements.

Once you create and share the GitHub repository, M0 through M2 are the first implementation target, followed by the small-scale training experiments in M3 and M4.

The ultimate deliverable is not just two model checkpoints. It is an auditable, reproducible system that can accept a natural-language request, generate a complete frontend, examine what it actually rendered, improve weak design decisions, and return working source code with evidence of its quality.
